# Guía de integración — frontend del MVP

Lo que un OpenAPI no puede decir. El contrato está en
[`backend/openapi.json`](../backend/openapi.json) y tiene los once endpoints con sus tipos,
sus constraints y sus diecisiete códigos de error; esto es el resto: en qué orden se llaman,
qué hacer con cada error, y las tres o cuatro reglas que si no se saben cuestan una tarde.

## Antes que nada: el 429

Los dos endpoints públicos que escriben —crear sesión y crear reserva— aceptan **cinco
peticiones por minuto y por IP**. Desarrollando el formulario de reserva eso se agota en
treinta segundos y la API empieza a devolver `429`, que parece que está rota y no lo está.

Levantala con el límite alto mientras desarrollás:

```bash
THROTTLE_LIMIT=1000 npm run start:dev
```

## Arranque

La API queda en `http://localhost:3100/api/v1`. Swagger interactivo en `/api/v1/docs`.

Para ver el contrato sin levantar nada, `backend/openapi.json` está versionado; `npm run spec`
lo regenera. Sirve para generar un cliente tipado, probado con esta versión:

```bash
npx openapi-typescript@7 backend/openapi.json -o src/lib/api.d.ts
```

Lo que sale de ahí compila con `tsc --strict`, los parámetros de la URL quedan tipados como
obligatorios, y los diecisiete códigos de error salen como una unión de strings, así que el
`switch` del manejo de errores se puede hacer exhaustivo y el compilador avisa si el backend
agrega uno.

El seed deja tres centros. El que importa es `lo-de-lili`, con los ocho tratamientos del
prototipo. `bella-piel` existe para probar que un centro no ve lo del otro, y
`centro-cerrado` está desactivado y responde `404` en todo, que es el caso de un link viejo.

La contraseña de los tres administradores sale de `SEED_ADMIN_PASSWORD` en el `.env` del
backend. Los usuarios son `lili@lodelili.test`, `admin@bellapiel.test` y `admin@cerrado.test`.

## El centro va en la URL

Todas las rutas cuelgan de `/tenants/{tenantSlug}`. Para el MVP el slug es `lo-de-lili` y se
puede hardcodear o sacar de una variable de entorno; el día que haya varios centros sale del
subdominio o del path, y el backend no cambia.

## Reservar son tres llamadas, ninguna con token

```
GET  /tenants/lo-de-lili/servicios?limit=100
GET  /tenants/lo-de-lili/servicios/{servicioId}/disponibilidad?fecha=2026-09-28
POST /tenants/lo-de-lili/reservas
```

**1. El catálogo.** Devuelve solo los tratamientos activos cuando se pide sin token, así que
lo que llega es exactamente lo que se puede reservar.

```json
{ "data": [ { "id": "cmucnsidt0002sif5kn0fmltb",
              "nombre": "Depilacion",
              "descripcion": "Elegimos la tecnica y la zona en una valoracion previa.",
              "duracionMinutos": 30,
              "precioCentavos": 1800000,
              "senaCentavos": 540000,
              "requiereValoracion": true,
              "activo": true } ],
  "nextCursor": "WyJEZXBpbGFjaW9uIiwiY211Y25zaWR0..." }
```

**2. La disponibilidad.** Cuelga del tratamiento y no del centro, porque la grilla depende de
la duración: uno de sesenta minutos tiene menos horarios que uno de treinta en la misma
franja. La fecha va como `YYYY-MM-DD`.

```json
{ "fecha": "2026-09-28",
  "data": [ { "hora": "09:00", "cuposDisponibles": 1 },
            { "hora": "09:45", "cuposDisponibles": 0 } ] }
```

**Un horario con `cuposDisponibles: 0` se pinta en gris, no se oculta.** La lista que devuelve
la API son todos los horarios que existen ese día; que estén completos es información para
quien mira, igual que en el prototipo. Si se filtran, la agenda de un día lleno se ve vacía y
parece que el centro no atiende.

**3. El alta.** Se manda la `fecha` y la `hora` tal como vinieron de la disponibilidad.

```json
POST /tenants/lo-de-lili/reservas
{ "servicioId": "cmucnsidt0006sif5nbcnoalw",
  "fecha": "2026-09-28",
  "hora": "09:00",
  "metodoPago": "efectivo",
  "clienteNombre": "Ana Perez",
  "clienteEmail": "ana@example.com",
  "clienteTelefono": "1155512345",
  "notas": "Primera vez" }
```

```json
201
{ "id": "cmucnsiip0018uqf5li9yc7a7",
  "fecha": "2026-09-28", "horaInicio": "09:00", "horaFin": "09:45",
  "estado": "confirmada", "metodoPago": "efectivo", "senaCentavos": 600000, ... }
```

`horaFin` y `senaCentavos` los calcula el servidor desde el tratamiento y **no se aceptan en
el body**: mandarlos devuelve `400`. La clienta no tiene cuenta, así que no hay registro ni
login en este flujo.

Con `metodoPago: "efectivo"` la reserva nace `confirmada`, porque la seña se cobra en el
local. Con `"mercadopago"` nace `pendiente`: todavía no hay integración de pagos, así que la
administradora la confirma a mano. Conviene que la pantalla de confirmación diga cuál de las
dos pasó.

## Qué hacer con cada error

Todos los errores tienen la misma forma. El `code` es para ramificar y el `message` ya viene
en español, listo para mostrar.

```json
{ "code": "slot_full", "message": "Ese horario ya no tiene cupo. Elegi otro." }
```

En el alta de reserva:

| `code` | HTTP | Qué pasó | Qué hacer |
| --- | --- | --- | --- |
| `slot_full` | 409 | Alguien lo tomó entre que se cargó la pantalla y se envió el formulario | Volver a pedir la disponibilidad del día y pedir que elija otro |
| `outside_business_hours` | 409 | La hora no está en la agenda: un domingo, o un horario que no es de la grilla | No debería pasar si la hora salió de la disponibilidad. Si pasa, refrescar |
| `past_date` | 409 | El turno ya pasó, o falta menos de dos horas | Refrescar: la pantalla estuvo abierta mucho tiempo, o el reloj del cliente está corrido |
| `too_far_ahead` | 400 | Más de noventa días | Acotar el calendario a noventa días |
| `servicio_not_found` | 404 | El tratamiento se dio de baja mientras la pantalla estaba abierta | Volver al catálogo |
| `validation_error` | 400 | Un campo del formulario | Mostrar el `message` al lado del campo |
| `high_contention` | 409 | Muchas reservas al mismo tiempo | **Reintentar**. Es el único que se resuelve solo |
| — | 429 | Se pasó el límite de peticiones | Ver el primer punto de esta guía |

En el resto:

| `code` | HTTP | Qué hacer |
| --- | --- | --- |
| `tenant_not_found` | 404 | El slug del centro está mal o el centro está inactivo. Es un error de configuración, no del usuario |
| `unauthenticated` / `invalid_token` | 401 | Mandar al login: falta el token o venció |
| `wrong_tenant` | 403 | El token es de otro centro. Cerrar la sesión y volver al login |
| `invalid_cursor` | 400 | Repetir la consulta sin `cursor` |

## Tres reglas del contrato

**La plata está en centavos enteros.** `senaCentavos: 540000` son $5.400,00. Se divide por
cien una sola vez, al mostrar. Son enteros y no decimales a propósito: un decimal sale como
string en el JSON y entra como número, y eso obliga a un `parseFloat` que tarde o temprano
pierde un centavo.

**Las horas son hora de pared del centro, no instantes.** `"09:00"` del `"2026-09-28"` es las
nueve de la mañana en el centro, sin zona horaria ni offset. No hay que convertir nada: se
muestra tal cual y se manda tal cual. Si se pasa por un `new Date()` con la zona del
navegador, el turno se corre.

**El cursor es opaco.** Se devuelve tal como vino, sin decodificar ni modificar. `nextCursor`
en `null` significa que era la última página. El catálogo entero entra en una sola página con
`?limit=100`; la paginación importa de verdad en el listado de reservas del panel.

## El panel de administración

```
POST /tenants/lo-de-lili/sesiones    → { accessToken, usuario }
```

```json
{ "accessToken": "eyJhbGciOiJIUzI1Ni...",
  "usuario": { "id": "cmucnsids0001sif5k2o0efku", "nombre": "Administradora", "rol": "admin" } }
```

El token va en `Authorization: Bearer <token>` y dura ocho horas. **Lleva adentro el centro al
que pertenece**: usarlo contra otro centro da `403 wrong_tenant`, aunque el slug de la URL sea
correcto. No hay endpoint de logout: el token no tiene estado en el servidor y cerrar sesión
es descartarlo.

Con token: el ABM de tratamientos, el `GET`/`PUT` de franjas de atención, el listado de
reservas y el cambio de estado. El listado sin filtro muestra también los tratamientos dados
de baja, que es lo que el ABM necesita administrar.

Cancelar un turno es `PATCH /reservas/{id}` con `{"estado":"cancelada"}`. Las transiciones
válidas son `pendiente → confirmada`, `pendiente → cancelada` y `confirmada → cancelada`;
`cancelada` es terminal y descancelar devuelve `409 invalid_transition`. Cancelar libera el
cupo.

El `PUT` de franjas **reemplaza la semana entera**: se manda la colección completa, no una
franja. La respuesta del `GET` sirve como body del `PUT` sin transformarla.

## Lo que la API todavía no hace

Para no diseñar pantallas contra algo que no existe:

- La clienta no puede cancelar ni reprogramar su turno. No hay con qué autenticarla.
- No hay integración real de Mercado Pago: no existe una URL de checkout que devolver.
- No se manda ningún mail. Ni confirmación ni recordatorio.
- No hay membresías, aunque el prototipo tenga el selector de planes.
- El centro y su horario se configuran por API, pero no hay alta de centros: los crea el seed.
