# Plan — TP Final: backend multi-tenant de turnos

## Context

`tp-final/` en este repo tiene solo la plantilla de la cátedra. La consigna pide una aplicación
completa —interfaz, servidor y datos que persisten— y que el repositorio conserve la evidencia del
proceso: el plan como archivo en disco, commits, branch y PR.

El producto es un **SaaS multi-tenant de turnos para centros de estética**. "Lo de Lili" es el primer
cliente y el que generó la idea, no el único: el diseño arranca multi-tenant, no se le agrega tenancy
después. El prototipo del front (https://lo-de-lili-prototipo.netlify.app/reservar) fija el flujo:
tratamiento → fecha y hora → tus datos → pago, y su bundle confirma la grilla real de horarios
(09:00 09:45 10:30 11:15 12:00 12:45 · 15:00 15:45 16:30 17:15 18:00 18:45: paso de 45 minutos con
pausa de mediodía).

Hoy Lili toma los turnos por WhatsApp y los anota a mano: turnos pisados, seña que se cobra según la
memoria, y una agenda que existe en una sola cabeza.

**Esta tarea es solo el backend.** El frontend Next.js lo hace Matías, consumiendo esta API, así que
el contrato de endpoints y el `docs-json` de Swagger son el entregable hacia el equipo.

## Alcance

**Entra:** catálogo de servicios con ABM · ventanas de atención configurables con capacidad ·
disponibilidad por servicio y fecha · alta pública de reserva con seña y método de pago ·
login de administrador con JWT atado a su tenant · listado y cambio de estado de reservas ·
paginación por cursor reutilizable · Swagger generado · linter y prettier · verificación por curl.

**Fuera de alcance, explícito:**

| Qué | Por qué |
|---|---|
| **Todo el frontend** | Lo hace Matías en Next.js. Este repo entrega la API y su spec OpenAPI. |
| Tests unitarios, de integración y e2e | Decisión tuya para esta entrega. La verificación es la corrida de curl, con request y response guardados. |
| SQL a mano: `EXCLUDE`, `CHECK`, `ALTER TABLE`, RLS | Decisión tuya: la migración es el baseline que genera Prisma y nada más. Lo que un `CHECK` cubriría vive en los DTO y los services (ver *Invariantes*). |
| Cuentas de cliente | El paso 3 del prototipo pide nombre, teléfono, email y notas, y ninguna contraseña. |
| SDK de Mercado Pago, checkout, webhook | Queda `metodoPago` y `senaCentavos`. La costura para MP son tres cambios aditivos. |
| Mails, recordatorios, membresías 1/3/6/12 | Fuera del MVP acordado. Las membresías cambian qué significa reservar: es otro MVP. |
| Super-admin de plataforma | Un solo rol `admin`, siempre atado a un tenant. Los tenants los crea el seed. |
| Varios profesionales, salas, feriados | La capacidad por ventana ya cubre "atiendo a 2 a la vez". Recursos nombrados es otro dominio. |

## Corrección a lo que te dije antes sobre las URLs

Te propuse un esquema híbrido: admin con el tenant en el JWT y URLs limpias (`/api/v1/servicios`), y
solo las rutas públicas con el slug en el path. **Lo reviso: el tenant va en el path siempre, también
en admin**, con el JWT como verificación.

El motivo es que el `POST /reservas` público no tiene token, así que el slug tiene que estar en la URL
de todos modos. Con el híbrido, el catálogo de servicios —que es el mismo recurso— queda colgando de
dos URIs distintas según quién lo lea, y hay que montar el mismo controller dos veces o duplicarlo.
Con el tenant siempre en el path hay una sola URI canónica por recurso, un solo árbol en Swagger, y
el `curl` dice a qué negocio le estás pegando.

La seguridad no se apoya en el path: el JWT lleva `tid` y **si no coincide con el tenant del path, es
403**. El cliente no elige su tenant, solo lo nombra; el token es la autoridad. El día del subdominio,
`lodelili.app.com` se resuelve en un middleware que inyecta el mismo slug y los handlers no cambian.

Tu intuición sobre el modelo de datos era la correcta y es la que se usa: tabla `Tenant` y `tenantId`
en cada tabla del dominio (shared schema). Es lo estándar; schema-por-tenant o base-por-tenant se
justifican con requisitos regulatorios que acá no hay.

## Aislamiento entre tenants

Tres capas, porque un `where` olvidado es una fuga de datos de otro negocio:

1. **Una Prisma Client Extension** (`$extends`) inyecta `tenantId` en el `where` y en el `data` de
   toda operación, leyéndolo de un `AsyncLocalStorage` que abre un middleware al inicio de la request.
   Ningún método de dominio recibe `tenantId` por parámetro: es justo el parámetro que, mal pasado a
   un `deleteMany`, borra la agenda de otro negocio.
2. **Un chequeo al arranque** recorre `Prisma.dmmf` y **tira la app** si hay un modelo sin columna
   `tenantId`. Es lo que convierte el único agujero silencioso del diseño en un crash al boot.
3. **Una FK compuesta** `Reserva(tenantId, servicioId) → Servicio(tenantId, id)`, que es lo único
   cross-row expresable en Prisma sin SQL a mano. Cubre lo que la extensión no ve: los `include`
   anidados.

`TenantContext.require()` **falla cerrado**: sin tenant en contexto no hay query. Y una regla de
ESLint prohíbe `$queryRaw`/`$executeRaw`, que es lo único que se escapa de la extensión.

El guard es global (`APP_GUARD`) y `@Public()` es la excepción: un endpoint nuevo al que se le olvida
el decorador queda **cerrado**, no abierto.

## Esquema

Una sola migración, `prisma migrate dev --name init`, generada por Prisma. Cinco modelos.

```prisma
generator client { provider = "prisma-client-js" }   // la extensión lee Prisma.dmmf de acá
datasource db   { provider = "postgresql", url = env("DATABASE_URL") }

enum RolUsuario    { admin }
enum EstadoReserva { pendiente confirmada cancelada }
enum MetodoPago    { efectivo mercadopago }

/// Raíz del árbol: el único modelo sin tenantId y el único que la extensión no filtra.
/// No hay endpoint que lo lea ni que lo liste. Los tenants se crean por seed.
model Tenant {
  id          String   @id @default(cuid())
  slug        String   @unique
  nombre      String
  /// La única razón por la que el backend conoce zonas horarias: saber qué hora es "ahora"
  /// acá, para rechazar turnos pasados. Todo lo demás es hora de pared.
  zonaHoraria String   @default("America/Argentina/Buenos_Aires")
  activo      Boolean  @default(true)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt
  usuarios    Usuario[]
  servicios   Servicio[]
  ventanas    VentanaAtencion[]
}

model Usuario {
  id           String     @id @default(cuid())
  tenantId     String
  email        String
  passwordHash String
  nombre       String
  rol          RolUsuario @default(admin)
  createdAt    DateTime   @default(now())
  updatedAt    DateTime   @updatedAt
  tenant       Tenant     @relation(fields: [tenantId], references: [id])
  /// El mismo email puede administrar dos centros. Por eso el login vive bajo el path del
  /// tenant: sin tenant, el email no identifica a nadie.
  @@unique([tenantId, email])
}

model Servicio {
  id                 String   @id @default(cuid())
  tenantId           String
  nombre             String
  descripcion        String?
  duracionMinutos    Int
  precioCentavos     Int
  senaCentavos       Int
  requiereValoracion Boolean  @default(false)
  activo             Boolean  @default(true)
  createdAt          DateTime @default(now())
  updatedAt          DateTime @updatedAt
  tenant             Tenant   @relation(fields: [tenantId], references: [id])
  reservas           Reserva[]
  @@unique([tenantId, nombre])
  @@unique([tenantId, id])    // no es decorativo: habilita la FK compuesta de Reserva
}

/// Franja recurrente en la que el centro toma turnos, con cuántos acepta en simultáneo.
/// capacidad > 1 ES el doble turno: configurable, no imposible.
model VentanaAtencion {
  id               String @id @default(cuid())
  tenantId         String
  diaSemana        Int    /// 1 lunes .. 7 domingo (ISO-8601)
  /// Hora de pared, "HH:mm" con cero a la izquierda: el orden lexicográfico coincide con el
  /// cronológico y Postgres lo resuelve con el índice.
  horaInicio       String @db.VarChar(5)
  /// Minuto más tardío en el que un turno puede TERMINAR, no cuándo se cierra la puerta.
  horaFin          String @db.VarChar(5)
  intervaloMinutos Int    @default(45)   /// separación entre inicios de la grilla
  capacidad        Int    @default(1)    /// turnos simultáneos aceptados
  tenant           Tenant @relation(fields: [tenantId], references: [id])
  /// Una franja por día y hora de inicio: es lo que hace idempotente al PUT de la colección.
  @@unique([tenantId, diaSemana, horaInicio])
}

model Reserva {
  id              String        @id @default(cuid())
  tenantId        String
  servicioId      String
  fecha           DateTime      @db.Date
  horaInicio      String        @db.VarChar(5)
  /// Snapshot: sobrevive a un cambio de duración del servicio, y el conteo de solapes no
  /// necesita join.
  horaFin         String        @db.VarChar(5)
  estado          EstadoReserva @default(pendiente)
  clienteNombre   String
  clienteEmail    String
  clienteTelefono String
  notas           String?
  metodoPago      MetodoPago
  senaCentavos    Int           /// snapshot del monto al reservar, como el precio en una factura
  createdAt       DateTime      @default(now())
  updatedAt       DateTime      @updatedAt
  /// FK compuesta: Postgres impide que una reserva apunte a un servicio de otro tenant
  /// aunque la aplicación se equivoque. El tenant se hereda del servicio.
  servicio        Servicio      @relation(fields: [tenantId, servicioId], references: [tenantId, id])
  @@index([tenantId, fecha, horaInicio])
}
```

**Decisiones de esquema:**

- **Ids `cuid()`.** Un id secuencial en un endpoint público delata volumen y convierte
  `PATCH /reservas/:id` en un `for` de 500 requests. Bonus: un id basura da 404, no 500.
- **`fecha @db.Date` + `horaInicio`/`horaFin` como `"HH:mm"`**, no `timestamptz`. El dominio es hora
  de pared del centro: "el martes a las 15:00" no cambia porque cambie una zona. Borra toda la
  aritmética de offsets y el caveat de DST, y el wire es simétrico (la disponibilidad devuelve
  `{fecha, hora}` y la reserva se crea mandando eso mismo).
- **Plata en centavos `Int`.** El `Decimal` de Prisma sale como string en JSON y entra como number:
  asimétrico. Con `Int` la validación `senaCentavos <= precioCentavos` no necesita librería.
- **`senaCentavos` y `horaFin` se copian a la reserva.** Si mañana sube el precio o cambia la
  duración, el turno de ayer conserva lo que la clienta aceptó.
- **Toda unique de dominio arranca con `tenantId`**, y toda FK a un hijo lo incluye. Es la regla para
  lo que venga.
- **`Reserva` no tiene FK a la ventana.** La ventana es una regla, no un evento: el PUT que reemplaza
  la colección borra filas, y una reserva es un compromiso con una persona.

## Disponibilidad y capacidad

`src/common/horario.ts` concentra la aritmética en funciones puras. `iniciosDeGrilla(ventana, duracion)`
es la **única** definición de qué horarios existen, y `ventanaDe()` la reusa: así el alta y la consulta
no pueden contradecirse, y un `12:10` se rechaza gratis.

Como `horaFin` es el minuto más tardío en que un turno puede *terminar*, la grilla depende del
servicio: con las ventanas del prototipo (`09:00→13:30` y `15:00→19:30`, intervalo 45) un servicio de
30 o 45 minutos da los 12 horarios exactos del prototipo, y uno de 60 pierde 12:45 y 18:45.

`GET .../disponibilidad?fecha=` devuelve todos los inicios futuros con `cuposDisponibles` (capacidad
menos los solapes vivos, con piso en 0), así el front los pinta en gris como el prototipo. Un día es
acotado: no se pagina.

**El sobrecupo se evita con `SERIALIZABLE` y reintento**, no con una constraint. `FOR UPDATE` y los
advisory locks necesitan `$queryRaw`, y un unique parcial solo expresaría cupos por hora de inicio, no
ocupación simultánea. `isolationLevel` es opción de primera clase de `$transaction`: cero SQL crudo.

```ts
return runSerializable(this.db, async (tx) => {
  // Leer las ventanas DENTRO de la transacción es lo que hace que un PUT de horarios
  // concurrente conflictúe con este alta en vez de pisarla.
  const ventanas = await tx.ventanaAtencion.findMany({ where: { diaSemana: diaSemanaISO(dto.fecha) } });
  const ventana = ventanaDe(ventanas, dto.hora, servicio.duracionMinutos);
  if (!ventana) throw new ConflictException({ code: 'outside_business_hours', message: '…' });

  const solapadas = await tx.reserva.findMany({
    where: { fecha: aDate(dto.fecha), estado: { not: 'cancelada' },
             horaInicio: { lt: horaFin }, horaFin: { gt: dto.hora } },   // rango semiabierto
    select: { horaInicio: true, clienteEmail: true },
  });
  if (solapadas.length >= ventana.capacidad) throw new ConflictException({ code: 'slot_full', … });
  // Doble submit del form público: con capacidad >= 2 entraban dos reservas idénticas.
  if (solapadas.some((r) => r.horaInicio === dto.hora && r.clienteEmail === dto.clienteEmail))
    throw new ConflictException({ code: 'reserva_duplicada', … });

  return tx.reserva.create({ data: { /* horaFin y senaCentavos salen del servicio */ } });
});
```

`runSerializable` reintenta hasta 3 veces ante `P2034` (el 40001 de Postgres), sin backoff: el tx que
ganó ya commiteó, el reintento inmediato lo ve.

**Bajar la capacidad con reservas ya tomadas se acepta y no cancela nada.** La capacidad es una regla
que se aplica al reservar, no un invariante sobre filas guardadas. Efecto: no entran reservas nuevas y
`cuposDisponibles` devuelve 0. Drena solo.

## Endpoints

Prefijo `api/v1`. Cuerpo de error siempre `{ code, message }`: código en inglés snake_case (es
identificador de máquina), mensaje en español (lo lee una persona).

|---|---|---|---|---|---|
| 1 | POST | `/api/v1/tenants/:tenantSlug/sesiones` | pública, throttle | 201 `{accessToken, usuario}` | 400 · 401 `invalid_credentials` · 404 `tenant_not_found` |
| 2 | GET | `.../servicios?limit&cursor&activo` | pública | 200 `CursorPage<Servicio>` | 400 `invalid_cursor` · 404 |
| 3 | GET | `.../servicios/:servicioId` | pública | 200 | 404 `servicio_not_found` |

| 5 | PATCH | `.../servicios/:servicioId` | admin | 200 | 400 · 401 · 403 · 404 · 409 |
| 6 | GET | `.../servicios/:servicioId/disponibilidad?fecha=` | pública | 200 `{fecha, data}` | 400 · 404 |
| 7 | GET | `.../ventanas-atencion` | admin | 200 `{data}` | 401 · 403 · 404 |
| 8 | PUT | `.../ventanas-atencion` | admin | 200 `{data}` | 400 · 401 · 403 · 409 `ventanas_superpuestas` |
| 9 | POST | `.../reservas` | **pública**, throttle | 201 | 400 `too_far_ahead` · 404 · 409 `slot_full`/`outside_business_hours`/`past_date`/`reserva_duplicada` |
| 10 | GET | `.../reservas?estado&servicioId&desde&hasta&limit&cursor` | admin | 200 `CursorPage<Reserva>` | 400 · 401 · 403 |
| 11 | PATCH | `.../reservas/:reservaId` | admin | 200 | 400 · 401 · 403 · 404 · 409 `invalid_transition` |
| — | GET | `/api/v1/docs`, `/api/v1/docs-json` | pública | Swagger UI / OpenAPI | — |

Once endpoints, ningún RPC y ningún `DELETE`. Por qué, donde importa:

- **`POST /sesiones`, no `/auth/login`.** `login` es un verbo en la URI; crear una sesión es crear un
  recurso, y devuelve 201. Sin `DELETE /sesiones/:id`: el JWT es stateless, el front tira el token.
- **No hay `DELETE /servicios/:id`.** La baja es lógica, y un DELETE tras el cual el recurso sigue
  existiendo es un contrato mentiroso. Es `PATCH {activo: false}`.
- **Cancelar es `PATCH /reservas/:id {"estado":"cancelada"}`**, no `POST .../cancelar`. Transiciones:
  `pendiente → confirmada|cancelada`, `confirmada → cancelada`, y `cancelada` es terminal (409
  `invalid_transition`). Que sea terminal cierra el sobrecupo por resurrección desde el panel.
- **`PUT /ventanas-atencion` reemplaza la colección entera y es idempotente** porque la
  representación no lleva `id`. El body del PUT y el del GET son el mismo `{data: [...]}`.
- **`?activo=` es un filtro común, no un flag de autorización.** El front del cliente pide
  `?activo=true`; el ABM pide sin filtro y ve todo. Un parámetro que cambia el nivel de autorización
  de una ruta pública es lo que se rompe en el segundo refactor.
- **No existe `GET /tenants` ni `GET /tenants/:slug`.** Listar los negocios publica la cartera de
  clientes, y el lookup individual filtraría `Tenant.id`, que es el claim `tid` del JWT.
- 200 GET/PATCH/PUT, 201 POST, 400 input malformado, 401 sin token o vencido, 403 token de otro
  tenant, 404 inexistente, 409 conflicto de dominio. Sin 204.

## Paginación por cursor

Cursor y no offset por el dominio: las reservas se ordenan por `fecha, horaInicio` y las altas entran
**en el medio** de ese orden. Con `OFFSET 20`, una reserva nueva para mañana corre todo un lugar y la
página siguiente repite una fila o saltea una — y una reserva salteada es una clienta que llega y no
está anotada.

**Keyset puro, dentro del `where`.** El `cursor`/`skip` de Prisma no pasa por la extensión de tenant:
un cursor forjado con un id ajeno entraría crudo al `findMany`. Con keyset el `where` del cursor va
adentro del `where` del llamador, así que la extensión lo sella y la fuga se cierra por construcción.

Una función, `paginate(query, claves, find)`, no un servicio inyectable ni una clase base: dos
llamadores, cada uno con su `where` y su `orderBy`, y ni un `if` por tipo de recurso.

```ts
return paginate(query, ['fecha', 'horaInicio', 'id'], (pagina) =>
  this.db.reserva.findMany({
    where: { ...filtros, ...pagina.where },
    orderBy: [{ fecha: 'asc' }, { horaInicio: 'asc' }, { id: 'asc' }],
    take: pagina.take,
    select: reservaSelect,          // ningún endpoint devuelve un modelo de Prisma sin select
  }),
);
```

Las `claves` siempre terminan en `id`: sin ese desempate el orden no es total —con capacidad > 1 hay
reservas con la misma fecha y hora— y el cursor saltea filas. El cursor es base64url de la tupla, se
valida antes de usarse (`invalid_cursor`, 400) y tiene tope de largo: es input público que termina en
un `where`. `take: limit + 1` resuelve "hay página siguiente" sin un `count()`.

`ApiCursorPage(Modelo)` es el único decorador de Swagger escrito a mano, porque los genéricos son lo
único que el plugin no infiere.

## Convención de idioma

**Los sustantivos del dominio y sus atributos en español; verbos, infraestructura y protocolo en
inglés. Identificadores en ASCII —sin tildes ni ñ—; textos para humanos en español rioplatense.**

| Capa | Ejemplos |
|---|---|
| Archivos y clases | `servicios.controller.ts`, `ServiciosService`, `CreateReservaDto`, `TenantAuthGuard` |
| Métodos | `servicios.findAll()`, `create()`, `update()`, `replaceAll()` — verbo inglés, sustantivo español |
| Funciones puras del dominio | `iniciosDeGrilla()`, `ventanaDe()`, `ahoraEn()`, `diaSemanaISO()` |
| Variables | `const servicio`, `const solapadas`, `const ocupados` / `const rows`, `const token` |
| Modelos y columnas | `Servicio`, `VentanaAtencion` · `duracionMinutos`, `senaCentavos`, `capacidad` / `id`, `tenantId`, `createdAt` |
| Enums | `EstadoReserva { pendiente confirmada cancelada }` — minúscula, es el valor del wire |
| Rutas y JSON | `/tenants/:tenantSlug/servicios/:servicioId/disponibilidad?fecha=` · `{ "cuposDisponibles": 2, "nextCursor": null }` |
| Códigos de error | inglés: `slot_full`, `outside_business_hours`, `invalid_cursor`, `wrong_tenant` |
| Mensajes de error | español: `"Ese horario ya no tiene cupo. Elegí otro."` |
| Comentarios y JSDoc | español; el JSDoc termina en Swagger |

`servicio.findAll()` es exactamente lo que pediste. "Seña" se escribe `sena` en el código
(`senaCentavos`) y "seña" en los textos. Cada validador lleva su `message` en español: son unas 30
strings a mano, a propósito, sin capa de i18n.

## Infra y tooling

- **`docker-compose.yml`**: solo `postgres:17-alpine`, puerto **5433** en el host para no chocar con
  un Postgres local, y `healthcheck` con `pg_isready` para que `up -d --wait` bloquee hasta healthy.
  La API corre fuera del compose: recompilar un contenedor en cada cambio no aporta nada.

## Invariantes sin constraint de base

Sin `CHECK` ni `EXCLUDE`, la integridad vive en los DTOs y los services. Los que no se recortan:

| Invariante | Dónde | Qué pasa sin eso |
|---|---|---|
| `duracionMinutos` 5..600 | DTO de servicio | Con 0, `horaFin == horaInicio`, el predicado de solape es vacío y **el control de capacidad queda desactivado** |
| `intervaloMinutos` 5..240 | DTO **y** guarda en `iniciosDeGrilla` | Con 0 el `for` es infinito: **proceso muerto desde un GET público**. Dos barreras porque es el único input que no da error sino un cuelgue |
| `capacidad` 1..20 | DTO | Capacidad gigante = sobrecupo autorizado; 0 = nada reservable en silencio |
| `fecha` = `YYYY-MM-DD` estricto | `@Matches`, **no** `@IsDateString` | `@IsDateString` acepta `2026-10-05T14:00:00Z`, que da `Invalid Date` y entra al `where` → **500 en endpoint público en vez de 400** |
| `horaFin = horaInicio + duracion`, seña del servicio | por construcción: ningún endpoint los acepta del body, más `whitelist` y `forbidNonWhitelisted` | Reserva con duración fabricada o seña $0 |
| ventanas del mismo día sin solapar, `horaFin > horaInicio` | `replaceAll`, en SERIALIZABLE | Dos capacidades para el mismo slot; día sin turnos sin ningún error |
| `cancelada` es terminal | `PATCH /reservas/:id` | Descancelar resucita una reserva sobre un cupo ya ocupado: **sobrecupo desde el panel, sin concurrencia** |
| `Reserva.tenantId == Servicio.tenantId` | FK compuesta en Prisma | Una reserva del tenant A toma precio y duración de un servicio de B |
| sobrecupo | `runSerializable` + el `findMany` de solapes | Dos POST simultáneos dejan 2 reservas donde entra 1 |
| `cursor` acotado y bien formado | DTO + `esTupla()` | Un cursor de 2 MB es un `JSON.parse` gigante gratis y sin token, y es input que termina en un `where` |
| slug del tenant normalizado | regex en el seed | `Lo-De-Lili` y homoglifos (`lo-de-lіli` con і cirílica) conviven como tenants distintos que un humano lee igual |

Aceptables de perder, con el motivo: que un `psql` a mano escriba lo que la API rechaza (es el costo
directo de no usar SQL a mano, y el upgrade el día que se levante es `CHECK` + RLS **sin tocar código
de aplicación**) · sobrecupo tras bajar la capacidad (decisión de negocio) · `pendiente` sin
expiración (retiene cupo hasta que el admin cancele) · la ocupación del negocio es pública (inherente
a cualquier UI de reservas: el prototipo ya pinta los ocupados en gris) · enumerar slugs de tenants
por el 404 vs 200 (inherente al diseño path-based; se acota no exponiendo nada del tenant) · un admin
no se puede desactivar mientras su token viva (el JWT no se revalida contra la base).
